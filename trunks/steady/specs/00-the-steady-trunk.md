# Steady Trunk · 00 The Steady Trunk

The **Steady Trunk**, code name `steady`, is intended to be Arbol's primary Trunk for everyday chat work. Its starting behaviour comes from the [Trivial Trunk specification](../../trivial/specs/00-the-trivial-trunk.md#requirements). The requirements below are a draft baseline for discussing what Steady should add or change.

Steady runs in the single Arbol installation described by [ARC-4](../../../../arbol/architecture/04-single-database.md) and uses the file layout in [ARC-5](../../../../arbol/architecture/05-where-arbol-keeps-its-files.md). Arbol can select it by its own code name. ARC-4 defines how the installation handles a start that omits the Trunk code name.

## Scope

This specification covers Steady's work inside a [Chat Exchange](../../../../arbol/GLOSSARY.md#chat-exchange), its Driver calls and conversation handling, and its program, Build and checks. [ARC-2](../../../../arbol/architecture/02-chat-exchange-across-components.md), [ARC-3](../../../../arbol/architecture/03-stuck-trunks.md) and ARC-4 govern the shared Exchange lifecycle. [DRV-2](../../../../arbol/driver-contract/02-inference.md) governs Driver inference, and [BLD-0](../../../../arbol/builds/00-builds-and-versions.md) governs Builds and the registry.

## Behaviour

At the baseline, Steady accepts a message, reads the chat history in the acceptance transaction and makes one Driver run on Arbol's chosen route. It streams events to the Exchange folder, saves completed messages and tool calls, and forwards stop and answer controls to the Driver. It ends the Exchange with the outcome of that run or the failure that forced it to stop.

Both detached and direct starts go through installation writer admission. Before acknowledging acceptance, Steady publishes the private Exchange folder and records the exact Trunk Build with the chat, message and open Exchange. If the database is unavailable when it has a pending end, Steady retains the folder. Settlement uses the recorded assignment, saves the result idempotently and performs only recovery work. See [ARC-4, Exchange lifecycle and persistence](../../../../arbol/architecture/04-single-database.md#exchange-lifecycle-and-persistence).

### Exchange Phases

An **Exchange Phase** is a stage of a Chat Exchange with a specific responsibility. It may do local work or contain one or more agent [Turns](../../../../arbol/GLOSSARY.md#turn). Durable acceptance and acknowledgement come before Intake. Steady writes and saves the Exchange end after Finalization. Recovery settles the recorded Exchange through the shared lifecycle.

#### Phase transitions

Steady starts Intake after acknowledgement. Each phase makes its hand-off by calling the next phase explicitly. Intake calls Planning when the request needs a plan, or calls Execution directly when the request can be handled immediately. Planning calls Execution with the plan available in the shared Exchange data. Execution calls Finalization with the outcome. Finalization hands that outcome back to the shared Exchange end handling.

| Phase | Responsibility | Initial implementation |
|---|---|---|
| **Intake** | Preserve the submitted message, gather initial context, classify the request and decide whether it needs Planning. | Prepare Cue Cards and call Planning. |
| **Planning** | Use the request, context and labels to decide how to approach work that needs a plan. | Pass through to Execution. |
| **Execution** | Answer the request or carry out the plan. Steady may supply a workflow or let the agent decide how to proceed. Agent tool interactions happen here. | Run the existing single Driver inference and retain its outcome. |
| **Finalization** | Inspect or classify the outcome when needed and run any wrap-up operations before the Exchange ends. | Pass the Execution outcome through to the shared end handling. |

For example, an agent can request a tool during Execution and resume in another Turn when it gets the result. Both Turns belong to the same Execution phase and the same Exchange. A Driver run can contain multiple Turns.

#### Phase data

Each phase owns its own **private phase data** for intermediate work. All phases can read and write the same **public Exchange data** for that Exchange. Before calling its successor, a phase writes any outputs the successor needs to the public data and passes it the same shared object. The successor starts with its own private data. Here public means shared across phases. Exchange Details reads the fields described below.

For example, Intake can put the request labels in the Exchange data and call Planning. Planning reads those labels, keeps its working notes private, writes the selected plan to the Exchange data and calls Execution.

Intake keeps its full prepared `systemPrompt` in its private data and copies the same value to the public Exchange data before calling Planning. An absent prompt is null in both places. Each phase has its own chronological `commands` list. Record the exact program, argument list and working directory for each subprocess the phase starts, plus the request or standard input when supplied. A Provider call records the Driver command and the complete Driver request that was submitted. Record tool calls reported by the Driver with the tool name and its arguments. A phase that starts no commands has an empty list. In particular, Planning remains a pass-through until it performs its own inference.

Run-time details are written as numbered UTF-8 JSON lines to `phase-details.jsonl` in the owner-only Exchange folder. A line has its increasing `n`, `phase` and one of `startedAt`, `finishedAt`, `command` or an Intake update with `privatePhase` and `publicExchange`. Each command has a `kind` (`subprocess`, `provider` or `tool`), its `command` and the applicable `arguments`, `workingDirectory`, `input` or `parameters`. Provider events report the effective route through the existing Driver event stream. Process environments and credential stores stay outside the details. The writer saves each detail with its Exchange and position in PostgreSQL from additive schema revision 4, using the same ordered saving and settlement as the response. Settlement replays complete lines after an interruption and tolerates a missing or torn journal. An unavailable journal or permanently refused diagnostic row does not change the outcome of the Exchange. Older compatible databases accept Steady runs without durable details. The journal follows the Exchange folder's usual cleanup.

#### Cue Cards in Intake

After acknowledgement, Intake uses Forester's non-hook `cues prepare` operation and Mycel's compiled catalog. Non-glossary Cue Cards match the accepted message and use the 8,000-character inline budget. Overflow goes into `cues.md` in the private Exchange folder and the context tells the agent to read it. Intake makes both the prepared turn context and glossary system instructions available to Execution through public Exchange data. Steady keeps the original message and saved history intact.

`forester cues prepare --exchange-json --overflow-file <absolute path>` reads a UTF-8 JSON object on standard input with `message` and `earlierMessages`, the earlier user messages from unreplaced Exchanges, oldest first. It returns `context` and `systemPrompt`, each a string or null. In `on` mode it returns an empty `context` when no non-glossary card needs delivery and null for both values when the catalog is unavailable. `off` returns empty `context` and null `systemPrompt`. `shadow` returns null for both so the normal hook can record its shadow result. An older Forester that rejects the option uses plain-text preparation and sends its cards as turn context. If preparation is unavailable or fails, Steady omits both values and the usual Driver and hook path applies.

The glossary matches terms in the accepted message and earlier unreplaced user messages. Each card appears once in first-mention order under `## Glossary`, with the introduction “The following terms are used in this conversation.” Use one subheading per term and the full prepared card body. The glossary uses the same source checks as turn context, substituting required-reading directions for changed sources and omitting missing ones. It has no Steady or Forester character limit and does not use the overflow file. Execution sends it as `systemPrompt` when there are entries and the Driver supports `cueContext`. In Codex, a changed system prompt can rebuild the native thread from Arbol history.

Drivers that support this extension advertise `capabilities.cueContext: 1` in `info`. On those Drivers, the optional `cueContext` field carries up to 8,000 characters of context for the current native turn. The Driver adds nonempty context at native submission as a labelled Cue Card block. It preserves the canonical `input`, history and continuity fingerprints. The field's presence, even with empty text, means Steady owns delivery on this run. For Claude and Codex it requires the validated Arbol chat marker. Those Drivers set `ARBOL_DISABLED_HOOK_FEATURES=cue-card-injection` in that run's native environment using [Forester's list of optional hook features](../../../../forester/specs/02-hooks.md#optional-hook-features). Forester skips selecting and injecting Cue Cards for the marked run, while the ordinary hook processing continues. Without the field, the Drivers omit the variable. Steady omits the field for older Drivers.

#### Exchange Updates

Intake emits [Exchange Updates](../../../../arbol/GLOSSARY.md#exchange-update) from the Cue Card preparation result. In first-mention order, report all included glossary term titles as “Glossary terms found: …”, or “No Glossary terms found” when an available catalog was checked and found none. In delivery order, report “Operational artifacts included: …” only when at least one included card points to an Operational Artifact under a corpus's `operations/` folder. Include artifacts delivered through the overflow file. A missing, disabled, shadowed or legacy preparation with no findings metadata leaves the corresponding update absent.

Store the title lists in a separate `exchangeUpdates` record in the existing Intake phase journal. Elma reads those records through the bounded phase-detail reader and renders them live and from saved Exchanges. The records contain display titles. The normal prompt, history and command records retain their existing shapes.

Elma shows “Inference started at …” above the response and “Inference ended at …” after it. Prefer the top-level Driver's actual start and finish times, including when those times are read back from saved runs. Leave a timestamp absent when its event was never recorded. Use the same smaller, muted styling for these updates and for the Intake findings. The pinned prompt is the sent-message record in the transcript.

During a Driver run, Steady counts Forester callbacks appended to the Ledger with the active chat's recorded Arbol identity. The installation admits one open Exchange per chat. Steady starts reading at the Ledger's current end immediately before the Driver starts, counts allowlisted callback names, and publishes changed totals as Execution Exchange Updates. Only callback names and counts leave the Ledger. Unavailable Ledger records and callbacks without the chat identity produce no update. Elma groups counts on one muted line during the run and reads the saved totals on reopen.

#### Elma Chat phase preview

The Elma Chat preview runs a fictional Exchange on demand. It chooses a fresh random delay of 5 to 20 seconds for each phase and shows one sample message when the phase starts and another when it finishes. The preview keeps the Exchange's current phase and each message's originating phase in local state. Messages follow the regular chat layout. A faint Ripples pattern and tint behind each group of messages is the only visible phase cue. Groups retain their backgrounds as the Exchange advances. At completion the transcript remains available, and Replay starts a fresh simulation.

Cmd-click anywhere in a tinted transcript region to inspect the Exchange and the phase that produced that region. Cmd+Enter on the focused region opens the same dialog. The compact dialog shows the Exchange identity and progress, the selected phase, the Exchange's public data and that phase's private data in a JSON tree. The data and close control are visible without a title bar. The top-level fields are visible on opening. Each nonempty object or array can expand or collapse independently, including nested objects inside arrays. Nested collections start collapsed. The selected phase's private data shows its `commands` in order. The preview uses fictional values with the same field shape as Steady's recorded details.

The popup displays at most the first 1,000 Unicode characters of a long text value followed by an ellipsis. For commands it shortens text payloads, including standard input, message text, Cue Card context and system instructions. It preserves executable names, arguments, working directories, keys, every parameter and collection entry, and exact values for configuration and tool arguments. The full values are used at runtime and stored in the Exchange details.

Live Elma opens the same popup from a Steady response with Cmd-click or Cmd+Enter. Intake findings, Driver content and the inference-end update carry their respective Intake, Execution and Finalization backgrounds. Cmd-click on a phase background selects that phase in the popup. The phase selector also reaches recorded phases with no transcript text. The renderer requests phase details through [the Bridge](../../../../arbol/backend/01-the-bridge.md#exchange-details) only while the popup is open. It reads new details during an open Exchange and makes a final read after settlement. Earlier Exchanges without details show an empty read state.

The Elma Storybook includes a separate comparison of 20 proposed phase backgrounds. Each option shows a geometric pattern and the existing tints across Intake, Planning, Execution and Finalization, with an enlarged fictional transcript for judging readability. The gallery preserves the design proposals. The selected Ripples treatment uses a static, low-contrast motif with phase-specific spacing across the normal chat canvas. Birch uses muted ochre for Intake, plum for Planning, pale honey for Execution and sage for Finalization, blended with the Birch canvas. The Execution tint and ripples are lighter than the Birch chat canvas. The ripples are brighter than the tint so they remain visible behind the transcript.

## Interface

Use `arbol-<driver>-driver run --control --request <exchange-folder>/run-1.json`. The request file has mode `0600` and contains the fields in STE-0.5 and STE-0.14. The Driver uses the supplied `chatSessionId` and history to resume or rebuild its conversation under [DRV-2](../../../../arbol/driver-contract/02-inference.md#the-conversation).

For capability preparation, query `info`, `subscriptions families` and `subscriptions list`. Require the selected Driver identity, contract version 1 or 2, and available Subscription families. Bound each query to five seconds and 256 KiB, and cancel preparation on stop. When `~/.arbol/pi-cutover.json` exists, check it before the queries and again before inference. In a nonterminal phase, block a route when the Driver matches a `blockedRoutes` entry and the Subscription matches or is unspecified on either side. A malformed or unreadable marker fails closed. See [Trivial's Driver capability and migration checks](../../trivial/specs/00-the-trivial-trunk.md#driver-capability-and-migration-checks).

## Open decisions

Which fields belong in each phase's private data and in the public Exchange data? Decide which of the shared fields Elma Chat should receive live, which belong in saved chat history, and which are needed only while the Exchange runs. The field definitions, persistence and Bridge interfaces remain open, along with the work each placeholder will take on.
